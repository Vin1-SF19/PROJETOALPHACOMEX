# DECISIONS — Decisões Técnicas Tomadas

### 2026-08-06 — Alpha Motion: Fase 08 implementa só Scroll Reveal + controles do player faltantes — Scroll Scrub/Sticky/Pinned/Parallax/Snap ficam documentados como limitação
**Contexto:** Fase 08 (Scroll/Scrollytelling e Controles do Player) da fila Alpha Motion. Investigação encontrou que `ModoApresentacaoClient.tsx` já é muito mais maduro do que o prompt original supõe estar faltando (setas, espaço, Escape, Fullscreen API com fallback silencioso, barra de progresso, número do slide) — mas `PlayerStandalone.tsx` (export standalone) não tem quase nada disso. `SlideScrollConfig` (Fase 01) e `on-scroll` (Fase 03) existem no modelo, mas sem NENHUM consumidor real.
**Decisão:** Implementar de fato apenas Scroll Reveal (via `IntersectionObserver`, isolado) e os controles de player que realmente faltavam (tecla R, velocidade, modo automático, toggle de reduzir animações, paridade mínima de teclado/fullscreen em `PlayerStandalone.tsx`). Scroll Scrub, Sticky Section, Pinned Section, Parallax e Scroll Snap NÃO foram implementados — todos exigiriam reestruturar a navegação de "slides discretos com transição" (arquitetura atual, usada em `PlayerStandalone.tsx`/`SlideApresentacaoLayer.tsx`/`ModoApresentacaoClient.tsx`) para "scroll contínuo de uma página", uma mudança arquitetural de alto risco que afetaria os três componentes simultaneamente.
**Alternativas rejeitadas:** Implementar os 6 modos de scroll da Seção 17 nesta fase — rejeitado por exigir uma reestruturação de navegação sem precedente/base testável no projeto, mesmo risco identificado e evitado nas Fases 05 (Push) e 06 (Morph, integração completa).
**Consequências:** `SlideScrollConfig.mode` continua aceitando os 4 valores no schema (`reveal`/`scrub`/`pinned`/`scrollytelling`), mas só `reveal` tem implementação real nesta fila. Os demais ficam reservados para trabalho futuro fora do escopo das 10 fases — pendência documentada, não inventada como pronta.

### 2026-08-06 — Alpha Motion: Morph implementado via `layoutId` do Framer Motion, não FLIP manual (clone/getBoundingClientRect)
**Contexto:** Fase 06 (Morph / Elemento Compartilhado) da fila Alpha Motion — tecnicamente a mais arriscada das 10 fases. O prompt original (Seção 22) pede um fluxo manual de 10 passos: capturar posição/dimensões via medição de DOM, criar camada temporária, clonar visualmente o elemento de origem, animar o clone, cleanup rigoroso. Investigação confirmou que **nenhum precedente desse tipo existe no projeto** — "Container Alpha" (a transição fullscreen mais complexa existente) usa `clip-path` com coordenadas calculadas matematicamente a partir de dados conhecidos, nunca `getBoundingClientRect()`/clone de DOM real. Todo o sistema de animação do projeto é declarativo (Framer Motion `variants`/`AnimatePresence`), nunca imperativo.
**Decisão:** Morph usa a feature nativa `layoutId` do Framer Motion (shared layout animations) em vez de reimplementar FLIP manualmente. O Framer Motion mede, anima e limpa automaticamente quando dois elementos compartilham `layoutId` e estão na mesma `LayoutGroup` — substitui os passos 2-10 do prompt original por uma API madura e testada pela própria biblioteca já em uso extensivo no projeto, eliminando o risco de reimplementar medição/clone/cleanup do zero sem nenhuma base de código para validar contra.
**Escopo desta fase:** cobre `texto`/`imagem`/`card`/`icone`/`botao` (tipos com layout previsível). Vídeo, 3D (`globo`/`particulas`/`objeto3d`) e containers com filhos complexos (`grid`) caem automaticamente no fallback Crossfade — mesmo padrão de recorte pragmático já usado para Push (Fase 05, documentado em `TransicaoSlide.tsx`).
**Alternativas rejeitadas:** FLIP manual (clone real do elemento DOM, `getBoundingClientRect` nos dois estados, camada temporária) — tecnicamente mais fiel ao prompt original, mas rejeitado por ser uma reimplementação do zero de uma técnica complexa e propensa a vazamento de memória, sem NENHUM precedente ou teste prévio no projeto para se apoiar.
**Consequências:** `sharedElementId` (já reservado no schema desde a Fase 01) agora vive em `baseComponenteSchema` — todo tipo de componente pode recebê-lo, mas só os 5 tipos elegíveis de fato acionam Morph via `layoutId`; os demais, mesmo com `sharedElementId` configurado, caem no fallback Crossfade silenciosamente (nunca erro).

### 2026-08-06 — Alpha Motion: transições de slide usam modelo híbrido (`transicaoEntrada` string + `SlideTransition` rica), e o editor ganha sua PRIMEIRA UI de seleção de transição
**Contexto:** Fase 05 (Transições entre Slides) da fila Alpha Motion. Investigação confirmou: `Slide.transicaoEntrada` (coluna Prisma `String?`, já existente) é o único campo realmente consumido em produção — via `TransicaoSlide.tsx`, usado idêntico no Modo Apresentação e no Export standalone, com fallback em fade e respeito a `useReducedMotion()`. Achado crítico: **não existia nenhuma UI no editor para escolher a transição** — a coluna nascia `null` e nunca era atualizada por nenhum fluxo.
**Decisão:** Modelo híbrido, sem migration: `transicaoEntrada` (string simples) continua servindo as transições Básicas (fade/crossfade/dissolve/slide/zoom simples) — suficiente, sem parâmetros ricos necessários. As transições complexas desta fase (Push, Wipe, Zoom cinematográfico, Background Crossfade — que precisam de `direction`/`intensity`/`backgroundMode`) usam `SlideTransition` completo (já modelado na Fase 01), salvo em `Slide.animacaoConfig.transition` (mesmo JSON `dadosJson`, sem coluna nova). `TransicaoSlide.tsx` passou a aceitar um `SlideTransition` opcional, priorizando-o quando presente; sem ele, cai no comportamento string original — retrocompatibilidade total.
**Consequências:** Esta é a PRIMEIRA vez que o editor expõe uma UI real para configurar a transição do slide (`SeletorTransicaoSlide.tsx`, na Barra Superior) — até aqui a coluna existia mas nunca era escrita por nenhuma ação do usuário. `AtualizarSlide` (`src/actions/slides.ts`) precisou ganhar capacidade de persistir `transicaoEntrada` como campo de coluna Prisma (não só dentro do JSON), separado da validação de `dadosJson`.

### 2026-08-06 — Alpha Motion: sem sistema de Undo/Redo real no editor — regra da Seção 28 do prompt original é aspiracional, não implementada
**Contexto:** Fase 04 (Timeline Visual) da fila Alpha Motion. O prompt original (Seção 28) pede que toda ação de animação gere "1 entrada de histórico" e que arrastes contínuos só commitem ao soltar o mouse. Investigação confirmou que o editor de apresentações NÃO tem nenhum sistema de undo/redo real hoje — `useEditorStore.versaoEdicao` existe só para invalidar respostas de autosave desatualizadas (`concluirSalvamento`), não é uma pilha de histórico. O padrão real e único usado em todo o editor (`useCanvasDragResize.ts`, `useTimelineDrag.ts`) chama `atualizarComponente` a cada evento `mousemove`, sem qualquer preocupação de "1 entrada por operação".
**Decisão:** `useTimelineDragV2.ts` (Fase 04) segue o MESMO padrão real já estabelecido (`atualizarAnimacaoElemento` chamado a cada `mousemove`), não implementa um sistema de commit-ao-soltar que não existe em nenhum outro lugar do editor. Implementar undo/redo de verdade apenas para esta fila seria inconsistente com o resto do produto e um escopo não pedido pelo usuário fora do prompt original.
**Consequências:** A regra da Seção 28 do prompt original permanece não atendida literalmente — documentado aqui como divergência consciente, não invenção silenciosa. Se o usuário quiser um sistema de undo/redo real no futuro, é uma feature transversal a todo o editor (não só animações), fora do escopo desta fila de 10 fases.

### 2026-08-06 — Alpha Motion: catálogo novo (Fase 02) grava em `Slide.animacaoConfig`, não em campo novo no componente
**Contexto:** Fase 02 (Animações Básicas) da fila Alpha Motion. O painel de propriedades atual (`AnimacaoProps.tsx`) e o motor real (`AnimacaoWrapper`/`variantsPara` em `nucleo.tsx`) são fortemente acoplados ao formato antigo `ConfigAnimacao` (1 animação de entrada por elemento, sem categoria/trigger/múltiplas animações) — reescrever "no lugar" para o novo modelo seria um risco alto de quebra. Scout recomendou arquitetura aditiva: novo catálogo/painel coexistem com os antigos, sem duplicar a implementação de cada animação (só 1 lugar por animação, o registry da Fase 01).
**Decisão:** As `ElementAnimation[]` do catálogo novo (Fase 02+) são gravadas em `Slide.animacaoConfig.timeline.animations[]` (já modelado e testado na Fase 01 — `resolverAnimacoesDoElemento()` já filtra por `elementId`), NÃO em um campo novo dentro de `baseComponenteSchema`. Evita duplicar "onde mora a animação de um componente" em dois lugares diferentes do schema.
**Consequências:** O painel novo (`AnimacaoPropsV2`, a criar) grava no slide inteiro (via ação que atualiza `animacaoConfig`), não no componente individual isolado — precisa de acesso ao `Slide` completo, não só ao `componente` como o painel antigo. `RenderComponente.tsx`/`nucleo.tsx` continuam sem alteração até uma fase futura conectar de fato o novo wrapper ao render (avaliado fase a fase, não antecipado). Painel antigo (`AnimacaoProps.tsx`) e novo coexistem temporariamente — consolidação/descontinuação do antigo não está no escopo desta fila de 10 fases, fica como pendência a decidir com o usuário depois.

### 2026-08-06 — Alpha Motion: Framer Motion continua sendo o motor de animação, GSAP não entra na Fundação
**Contexto:** Prompt mestre extenso do usuário pedindo sistema profissional completo de animações/transições para o editor de apresentações (módulo renomeado nesta sessão de "Alpha Presentation Studio" para "Alpha Motion"), quebrado em 10 fases via `prompt-phases/` (`concluidos/AlphaMotion/` ao final). Na Fase 01 (Fundação), Scout investigou se GSAP (instalado desde a Onda 3, 2026-07-09, sem nenhum uso de código) deveria virar a base do motor de tempo/easing/timeline pedido pelo prompt.
**Decisão:** O motor de animação real do módulo já é **Framer Motion declarativo** (`AnimacaoWrapper`/`FilhosContainer` em `nucleo.tsx`, `variantsPara()` traduzindo `ConfigAnimacao` em variants `initial/animate/transition`) — e já roda idêntico tanto no Editor quanto no HTML exportado standalone (o player exportado NÃO é um motor JS separado, é a mesma árvore React/`RenderComponente` compilada via esbuild para bundle autocontido, `PLAYER_JS`/`PLAYER_CSS`). A Fundação (Fase 01) estende esse motor com a interface `AnimationController`/registry central pedidos pelo prompt (Seções 20/21), envolvendo o Framer Motion existente — não o substitui, não instala GSAP. Reafirma a regra do próprio prompt original (Seção 2, item 8: "evite instalar múltiplas bibliotecas que façam a mesma coisa") e o padrão já documentado em `.bibble/rules/styling-rules.md` ("Framer Motion — para animações de entrada/saída, gestos").
**Alternativas rejeitadas:** GSAP como motor primário — rejeitado por já existir motor funcional em produção (Framer Motion) cobrindo o mesmo espaço, e por GSAP nunca ter sido usado em código real apesar de instalado.
**Exceção reservada, não decidida agora:** GSAP (`ScrollTrigger`, plugin `Flip`) pode ser justificado pontualmente nas Fases 04 (Timeline)/06 (Morph)/08 (Scroll Scrub) SE Framer Motion (`useScroll`/`useTransform`/`AnimatePresence`) não cobrir scroll-scrub ou o FLIP do Morph com qualidade suficiente — decisão a tomar (e documentar aqui) na fase específica, não antecipada na Fundação.
**Consequências:** Todo o catálogo de animações das Fases 02-09 deve ser registrado como variants/hooks do Framer Motion, consumidos pelo mesmo `AnimationController`. Também identificado nesta investigação: já existe uma transição fullscreen cinematográfica própria em produção, "Container Alpha" (`animacao-container-alpha.ts`, `TransicaoContainerAlphaLayer.tsx` — porta abre, câmera avança, disparada no 1º gesto do usuário) — as Fases 05/06 (Transições/Morph) devem tratá-la como uma entrada do novo registry, nunca recriar equivalente do zero.

### 2026-07-31 — Modelo padrão do Bibble trocado de `gemma4:e4b` para `qwen3:14b`
**Contexto:** Investigando o bug de falsa confirmação de abertura de chamado (Bibble alegava "chamado #PAA-2026/789 criado" sem a tool nunca ter rodado — ver `known-errors.md`), o usuário perguntou qual IA está no Bibble e quais opções existem para trocar. O modelo padrão em uso era `gemma4:e4b` (8B, denso), um dos mais propensos a pular tool calls e alucinar confirmações.
**Decisão:** Trocado `BIBBLE_MODEL`/`NEXT_PUBLIC_BIBBLE_MODEL` em `.env.local` para `qwen3:14b`. Antes de decidir, medimos latência real (não estimada) no servidor Ollama do projeto (`192.168.35.113:11434`) com o mesmo formato de chamada do Bibble (tool definitions reais, prompt de abrir chamado): `qwen3:14b` respondeu em **8,5s**, `qwen3.6:35b` e `qwen3.5:35b-a3b` em **~22s** (ambos MoE, mas ainda ~2,6x mais lentos que o 14B neste hardware — a arquitetura MoE não compensou a diferença de tamanho aqui). Os três chamaram a tool corretamente no teste.
**Alternativas rejeitadas:** Qwen 3.6 · 35B (mais "confiável" em teoria, mas quase 3x mais lento sem ganho comprovado de confiabilidade que justifique — a proteção estrutural do `chamado-guard.ts` já cobre alucinação residual independente do modelo escolhido). OpenAI/Anthropic/Google: não têm API key configurada em `.env.local`, ficariam indisponíveis mesmo aparecendo na lista de seleção da UI.
**Consequências:** Qualquer modelo Ollama listado em `PROVIDER_MODELS.ollama` ([client.ts](../../src/lib/bibble/client.ts)) funciona de fato (servidor já configurado). Provedores externos (OpenAI/Anthropic/Google) aparecem no seletor mas precisam de API key adicionada em `.env.local` antes de funcionar. Se no futuro a latência do 14B se tornar aceitável em troca de mais confiabilidade, reavaliar com o mesmo método de benchmark real (nunca estimar por tamanho nominal do modelo).

### 2026-07-28 — Gestão de Comissões e Prêmios: decisões arquiteturais chave (Fases 01-16)
**Contexto:** Módulo completo executado via fila `prompt-phases/` (17 fases). O prompt original deixava algumas decisões em aberto, resolvidas com o usuário durante a execução (não inventadas).
**Decisões:**
1. **Cargo: `CargoColaborador` estendido (ganhou `setorId`/`vinculoPadrao`/`naturezaRecebimento`/`permiteMultiplosOcupantes`), não tabela paralela.** Usuário escolheu a opção recomendada pelo Scout em vez de criar um model `CargoComissao` separado, evitando duplicar a fonte de verdade de cargos.
2. **Fonte de contratação: merge de `ContratoComercial` + `clientes`, nunca uma fonte só.** Usuário pediu explicitamente "união dos dois para não ficar faltando nenhum dado" — `company-event-merger.ts` reconcilia os dois adapters.
3. **Vínculo CLT/PJ: já é literal em `ContratoColaborador.tipo`**, não precisou de mapeamento novo — confirmado pelo usuário na Fase 01 (Scout havia levantado como pergunta bloqueante).
4. **Êxito (PROCESS_SUCCESS) nasce de `clientes.dataExito`** (CS&NPS) passando de vazio para preenchido — não do Checklist RADAR, não é registro manual. Confirmado pelo usuário na Fase 01.
5. **RBAC do módulo é módulo-inteiro** (`permission: 'comissoes'` no registry, `allowedRoles`), não por ação. RBAC granular por ação dentro do módulo ficou como TODO documentado em texto em todos os 12 arquivos de Server Actions — decisão implícita de escopo (a Fase 14, "Configurações", não chegou a implementar um sistema de permissões granulares novo, e isso não foi resgatado antes do fechamento da Fase 16).
6. **Ajuste manual (`ManualAdjustment`) tinha schema e UI de leitura desde a Fase 02/10, mas nenhuma Server Action de escrita** — diferente de "Novo Lançamento" (marcado conscientemente `BotaoEmBreve` desde a Fase 09), este ficou esquecido sem nota até o Sage (Fase 16) encontrar a lacuna comparando contra a seção 37 do prompt original. Usuário escolheu implementar imediatamente: `CriarAjusteManual` cria `ManualAdjustment` + `EntryComponent` tipo AJUSTE com a DIFERENÇA (nunca reescreve componentes originais do motor de regras), recalcula `totalCents` via `$transaction`, bloqueia ajuste em lançamento já Pago/Estornado, grava `CommissionAuditLog`. Aprovação do ajuste (`aprovadoById`/`aprovadoEm`) fica como ação separada, ainda não implementada — próximo débito conhecido.
7. **Desconto acima de 10% NUNCA decide sozinho** — exige `politicaDescontoAcimaDe10` explícita (5 opções: USAR_VALOR_PAGO, USAR_TARIFARIO, EXIGIR_APROVACAO, BASE_MANUAL, FORA_DO_PADRAO). Sem política configurada, a base fica `0` e `requiresApproval: true` — nunca um fallback silencioso.
**Alternativas rejeitadas:** tabela `CargoComissao` paralela (rejeitada — duplicaria fonte de verdade); usar só `ContratoComercial` OU só `clientes` para contratação (rejeitado pelo usuário — perderia dado de uma das fontes).
**Consequências:** Antes de usar o módulo com dados reais de colaboradores/pagamentos, o usuário deve estar ciente das pendências conscientemente deixadas configuráveis (seção 39 do prompt original): fórmula definitiva do DSR (`dsr-formula.ts` tem placeholder), natureza do valor do Diretor Operacional, feriados municipais, tratamento de inadimplência. Ver `architecture.md` e `codebase-map.md` para detalhe técnico completo.

### 2026-07-27 — Alpha Blueprint: divergências corrigidas do prompt original antes de implementar
**Contexto:** O prompt original do usuário (executado via fila `prompt-phases/`) especificava um schema conceitual e algumas escolhas de stack que não batiam com o estado real do projeto. O Scout mapeou essas divergências ANTES de qualquer implementação, e elas foram corrigidas com aprovação de Vault/execução de Echo.
**Decisões:**
1. **FK de usuário é `Int`, não `String`/cuid.** O schema conceitual do prompt usava `requesterId String` etc. — mas `usuarios.id` é `Int @autoincrement()` neste projeto. Todas as 9 tabelas novas (`BlueprintProject` e as 8 filhas) usam `Int` para toda referência a usuário.
2. **`setor` é `String?` livre, não uma FK.** Não existe model de Setor dedicado — setor é `usuarios.role` como texto, mesmo padrão já usado em todo o resto do sistema (POP/Confirmação de Leitura, GestaoColaboradores, etc).
3. **Upload via Vercel Blob dedicado, não UploadThing.** UploadThing está no `package.json` mas nunca foi configurado/usado em nenhuma rota real do projeto — só existe como dependência morta. Vercel Blob é o mecanismo real em produção. Usuário forneceu um store dedicado (`BLUEPRINT_STORE_ID`/`BLUEPRINT_READ_WRITE_TOKEN`) durante a implementação, seguindo o mesmo padrão multi-store já usado (`IACHAT_*`, `COMISSOES_*`, `SKILLS_*`, `HOLERITES_*`).
4. **IA via Ollama real (`callCompletion`), não Anthropic direta.** Apesar do `CLAUDE.md` apontar Claude API como "futuro padrão" para o assistente Bibble, a implementação real em produção hoje usa Ollama (function-calling clássico `OllamaTool[]`, formato OpenAI-compat). A IA do Alpha Blueprint segue a infraestrutura REAL, não a aspiracional — reaproveita `callCompletion`/`encodeSSE` de `lib/bibble/completion.ts`, com tools isoladas por módulo (`BLUEPRINT_AI_TOOLS`, nunca misturadas com as tools gerais do Bibble).
5. **Tiptap como editor rico** — nenhum editor de texto rico existia no projeto antes; Tiptap foi escolhido e instalado (compatibilidade com React 19 confirmada antes de instalar), conforme já sugerido como primeira opção no prompt original.
6. **`@xyflow/react` já estava instalado** (usado em modo visualização pelo Apresentation Studio, tipo `grafo`) — reaproveitado para o canvas do Blueprint em modo totalmente editável, sem precisar avaliar React Flow como alternativa nova (já era a mesma lib).
**Consequências:** Esse é o segundo módulo do projeto (depois do Apresentation Studio) a reaproveitar `callCompletion`/streaming SSE para uma feature de IA fora do chat principal do Bibble — o padrão de "IA de módulo específico, isolada, reaproveitando a infraestrutura de completion" está se consolidando como o caminho certo para features de IA localizadas, em vez de estender o Bibble genérico.

### 2026-07-27 — Fila de fases de prompt: `prompt-phases/` (execução sequencial pelo próprio Bibble)
**Contexto:** Usuário pediu um lugar para depositar múltiplas fases de prompt (uma tarefa longa quebrada em vários passos) e uma rotina que as execute em sequência até o fim, avisando ao concluir.
**Decisão:** Pasta `prompt-phases/` na **raiz do projeto** (não em `.bibble/`), com **1 arquivo `.md` por fase**, numerado (`01-nome.md`, `02-nome.md`...). Execução é feita pelo **próprio Bibble na sessão** (não script externo chamando a API) — ele lê cada arquivo em ordem numérica e o processa como se fosse uma mensagem do usuário, seguindo o fluxo normal de agentes quando aplicável (Scout → implementação → Forge → etc.), avança só após concluir/reportar a fase atual, e avisa o usuário ao terminar a fila inteira. Pasta é **git-ignored** (`/prompt-phases/` adicionado ao `.gitignore`) — é fila de trabalho local/operacional, nunca deve ir para o repositório. Progresso é rastreado em `prompt-phases/_status.md` (também ignorado), permitindo retomar caso a sessão seja interrompida no meio da fila. Documentação de uso em `prompt-phases/README.md`.
**Alternativas rejeitadas:** Script Node/TS chamando a API da Anthropic diretamente — rejeitado pelo usuário, que quer que o próprio Bibble (dentro da sessão do Claude Code) processe as fases, não um processo externo desacoplado.
**Consequências:** Ao ler "Bibble, executa as fases de prompt" (ou variações), o Bibble deve: listar arquivos `.md` numerados em `prompt-phases/` (ignorando `README.md`/`_status.md`), ordenar numericamente, processar um por vez, atualizar `_status.md` a cada fase concluída, e só reportar sucesso final depois que TODOS os arquivos da fila tiverem sido processados.

### 2026-07-14 — Padrão reutilizável "Vídeo Introdutório por módulo" (estreado no módulo Parceiros)
**Contexto:** Usuário pediu um botão "Vídeo Introdutório" no topo do módulo Parceiros: Admin clica e abre modal com player + painel de configuração (seleciona vídeo já cadastrado no Alpha Skills, com busca por módulo/curso/nome), botão "Ativar Vídeo Introdutório" no rodapé do painel. Usuário não-Admin clica e vê só o vídeo escolhido, sem o painel. Uma vez ativado, o botão fica visível para todos os usuários (não-admin) por 7 dias corridos; depois disso, SOME da tela para não-admin (mas não é apagado do banco — soft-expire, mantém o registro). Para o Admin, o botão nunca some (sempre pode reconfigurar, mesmo com a config expirada para os demais). Usuário pediu explicitamente que este esquema seja **genérico e reutilizável em outros módulos do PainelAlpha no futuro** — não é feature isolada do módulo Parceiros.
**Decisão:** Novo model Prisma **cross-módulo** `VideoIntrodutorioConfig` (`modulo: String @unique`, `videoId: String?` → FK para `videos` do Alpha Skills, `ativadoEm: DateTime?`, `ativadoPorId: Int?` → FK `usuarios`, ambas FKs com `onDelete: SetNull`) — 1 registro por módulo, sempre representando o estado ATUAL (não histórico; ativar de novo sobrescreve `videoId`/`ativadoEm`, não cria linha nova). O campo `modulo` usa o mesmo identificador canônico de `MODULOS_REGISTRY` (ex: `"parceiros"`). Cálculo de expiração (`ativadoEm + 7 dias`) acontece em TODA leitura (`obterVideoIntrodutorioConfig`), nunca via cron/job — o projeto não tem infra de cron confirmada, e soft-expire por cálculo em runtime é mais simples e suficiente. A visibilidade do botão para Admin vs. não-Admin é decidida no componente que renderiza (Admin sempre vê o botão, mesmo com config expirada; não-Admin só vê se `ativadoEm` existe E está dentro dos 7 dias), nunca escondendo o dado bruto da Server Action.
**Alternativas rejeitadas:** Model `id Int @default(1)` singleton por módulo (padrão de `ParceiroConfig`) — rejeitado explicitamente por não escalar para múltiplos módulos (seria necessário 1 tabela nova por módulo). Histórico de todas as ativações (1 linha por ativação, nunca sobrescrita) — rejeitado, usuário confirmou que só o estado atual é necessário; a garantia de "não apagar" já é satisfeita pelo soft-expire (a config nunca é deletada, só para de ser exibida).
**Consequências:** Componentes genéricos ficam em `src/components/VideoIntrodutorio/` (fora de qualquer pasta de módulo específico — primeiro precedente cross-módulo do projeto fora de `components/ui/`/`components/layout/`): `BotaoVideoIntrodutorio` (recebe `modulo: string` + `isAdmin: boolean`), `ModalVideoIntrodutorioAdmin` (player + painel de seleção + botão ativar), `ModalVideoIntrodutorioUsuario` (só player), `PainelSelecaoVideoSkills` (busca combinada módulo/curso/vídeo), `PlayerVideo` (wrapper de `<video>` nativo — vídeos do Alpha Skills são sempre upload direto via Vercel Blob, nunca embed externo, confirmado em `Upload.tsx`). Para plugar em um módulo futuro: buscar `obterVideoIntrodutorioConfig("nome-do-modulo")` no Server Component da página, passar como prop, renderizar `<BotaoVideoIntrodutorio modulo="nome-do-modulo" isAdmin={...} />` no header. Limitação conhecida: a checagem de permissão usa `isAdminRole()` global (`role === "Admin" || role === "CEO"`, de `src/lib/onyx/ownership.ts`) — se um módulo futuro tiver regra de permissão diferente (ex: Metas restrito a "Lider Comercial"), a Server Action `ativarVideoIntrodutorio` vai precisar de um parâmetro de autorização customizável, não coberto nesta primeira implementação.

### 2026-07-13 — REGRA PERMANENTE: Parceiros ↔ Metas ↔ CS&NPS são módulos acoplados via `clientes` — qualquer migration em `clientes` exige checar os 3
**Contexto:** O incidente de FK fantasma (`clientes_old`, ver entradas seguintes) não afetou só as tabelas satélite do CS&NPS (`socios`/`log_cs`/`logFeedback`/`logAlteracao`) — ao investigar um bug real reportado pelo usuário no módulo Parceiros ("Erro ao vincular a indicação", sem log nenhum no console porque o `catch` do código engolia o erro), descobriu-se que `indicacoes` (tabela do módulo Parceiros, FK `clienteId → clientes`) também tinha a mesma FK fantasma. Uma varredura completa do banco (`PRAGMA foreign_key_list` em TODAS as tabelas) encontrou ainda mais vítimas do mesmo incidente: `crm_oportunidades` e `crm_contatos` (tabelas de CRM, também FK para `clientes`). Ou seja, o dano de uma migration em `clientes` se espalhou por 3 módulos que pareciam, à primeira vista, independentes.
**Decisão:** **Parceiros, Metas (ContratoComercial) e CS&NPS (clientes) NÃO são módulos independentes — são acoplados pela tabela `clientes` como hub central.** Tabelas de um módulo têm FK direta ou indireta para `clientes`: `Indicacao.clienteId` (Parceiros), `crm_oportunidades.clienteId`/`crm_contatos.clienteId` (CRM), `socios`/`log_cs`/`logFeedback`/`logAlteracao`/`HistoricoAlteracaoCliente` (CS&NPS satélites), e o próprio fluxo de sincronização automática Metas→CS&NPS (`criarRegistroClienteAPartirDeContrato`, chamado por `confirmarFechamento` em `ContratoComercial.ts`) escreve diretamente em `clientes`.
**REGRA OBRIGATÓRIA a partir de agora:** Toda vez que houver QUALQUER mudança estrutural na tabela `clientes` (rename, recriação, mudança de tipo de coluna, remoção de coluna, mudança de constraint/índice) — antes de considerar a migration concluída, é OBRIGATÓRIO:
1. Rodar `PRAGMA foreign_key_list` em TODAS as tabelas do banco (não só nas que a migration pretende tocar) — já era regra desde o incidente original, reforçada aqui.
2. Verificar explicitamente as tabelas dos 3 módulos acoplados: **Parceiros** (`indicacoes`, `parceiro_endereco`, `parceiro_responsavel` se tiverem FK indireta), **Metas/Comercial** (`ContratoComercial` e qualquer tabela que referencie `clientes` a partir do módulo comercial), **CRM** (`crm_oportunidades`, `crm_contatos`), e **CS&NPS satélites** (`socios`, `log_cs`, `logFeedback`, `logAlteracao`, `HistoricoAlteracaoCliente`).
3. Testar manualmente (ou pedir para o usuário testar) um fluxo de cada um dos 3 módulos após qualquer migration em `clientes` — não basta o CS&NPS funcionar, Parceiros e Metas precisam ser validados também.
4. Vault deve recusar aprovar qualquer migration em `clientes` que não venha acompanhada dessa checagem cross-módulo.
**Consequências:** Bibble/Scout devem tratar qualquer pedido de mudança em `clientes` como potencialmente impactando os 3 módulos, mesmo que o pedido do usuário mencione só um deles. Scout deve incluir essa checagem no blueprint sempre que `clientes` estiver no escopo.

### 2026-07-13 — INCIDENTE: perda de dados em socios/log_cs/logFeedback/logAlteracao (FK fantasma pós-migration)
**Contexto:** A migration de `clientes` desta sessão (rename `clientes`→`clientes_old`, criar `clientes` nova sem `cnpj @unique` sozinho, copiar dados, `DROP TABLE clientes_old`) não considerou que 4 tabelas satélite (`socios`, `log_cs`, `logFeedback`, `logAlteracao`) tinham FK com `ON DELETE CASCADE` apontando para o NOME `clientes_old`. O `ALTER TABLE RENAME` do SQLite não atualiza automaticamente FKs de OUTRAS tabelas que referenciam pelo nome antigo — e o `DROP TABLE clientes_old` subsequente, com essas FKs ainda ativas e em cascade, apagou o conteúdo dessas 4 tabelas. Descoberto só quando um usuário tentou editar um cliente e o INSERT em `logAlteracao` falhou com `no such table: main.clientes_old` (a FK "sobreviveu" ao DROP como uma referência fantasma, porque o SQLite só bloqueia o INSERT, não o DROP em si). Confirmado via query direta no Turso: as 4 tabelas têm 0 registros, mesmo com 239 clientes reais existentes — perda de dado real de sócios cadastrados e históricos de CS/feedback/alteração. **Não havia backup dessas 4 tabelas** (o backup pré-migration só cobriu `clientes`) — dado irrecuperável.
**Decisão:** Corrigida a FK de `logAlteracao` (agora aponta para `clientes` corretamente, tabela recriada via transação atômica). Usuário decidiu reconstruir a lógica de log de auditoria do zero (ver decisão seguinte), em vez de restaurar o sistema antigo.
**Atualização (mesmo dia, escopo ampliado):** o mesmo incidente também atingiu `indicacoes` (módulo Parceiros — causou o bug real "Erro ao vincular a indicação", sem log no console porque o `catch` do código engolia o erro) e `crm_oportunidades`/`crm_contatos` (CRM). Uma varredura completa (`PRAGMA foreign_key_list` em TODAS as tabelas do banco) confirmou 6 tabelas afetadas ao todo: `socios`, `log_cs`, `logFeedback`, `crm_oportunidades`, `crm_contatos`, `indicacoes` — todas com 0 registros (mesma perda de dado do incidente original, agora com escopo confirmado). **Todas as 6 foram corrigidas** (Vault aprovado, SQL gerado a partir do schema REAL do Turso — não do `schema.prisma` — para preservar corretamente colunas adicionadas via `ALTER TABLE` e índices/FKs adicionais como os 3 índices de `indicacoes`, incluindo o `UNIQUE` em `clienteId`). Verificado pós-correção: todas as 6 com FK apontando para `clientes` (não mais `clientes_old`), contagens preservadas (0 antes/depois, sem perda adicional). Ver regra permanente sobre acoplamento entre módulos logo acima nesta mesma memória.
**Regra permanente adotada:** **Antes de qualquer `DROP TABLE` em produção, rodar `PRAGMA foreign_key_list` em TODAS as tabelas do banco (não só nas que a migration pretende tocar) para achar referências por nome à tabela que vai ser dropada.** Se algo apontar para o nome antigo, corrigir a FK ANTES do drop, nunca depois. Vault deve exigir essa checagem explicitamente em toda migration futura que envolva rename+drop de tabela.
**Consequências:** Perda permanente de histórico de sócios cadastrados e logs de CS/feedback/alteração anteriores a 2026-07-13. Novo sistema de log (ver decisão seguinte) nasce sem histórico herdado — timeline "zerada" a partir de agora.

### 2026-07-13 — Reconstrução do log de auditoria do CS&NPS: model `HistoricoAlteracaoCliente`
**Contexto:** Consequência direta do incidente acima. O sistema antigo (`logAlteracao`) salvava snapshot JSON do cliente INTEIRO a cada save (mesmo mudando 1 campo só), sem `userId` real (só string de nome via `getColaboradorNome()`), sem granularidade por campo, e permitia só "restaurar" o registro inteiro de volta (sobrescrevendo edições feitas depois). Usuário pediu reconstrução "com lógica melhor e mais estruturada", não religar o sistema antigo.
**Decisão:** (1) **Granularidade por campo**: cada campo alterado em 1 save vira 1 linha de log (`campo`/`valorAnterior`/`valorNovo`), não mais 1 snapshot JSON gigante. (2) **Autoria**: `userId Int?` (FK real para `usuarios`, via `auth()`/`session.user.id` — que é string na sessão, precisa `Number()`) + `nomeUsuarioNaEpoca String` (snapshot do nome, sobrevive a rename/desativação do usuário). FK usa `onDelete: SetNull` (não Cascade) — se o usuário for deletado de verdade um dia (hoje só existe INATIVO, nunca delete real), o histórico permanece intacto, só perde o vínculo de FK. (3) **Reversão por campo específico**: cada linha de log é revertível individualmente, não mais o cliente inteiro de uma vez. (4) **Agrupamento por `loteId`**: cada ação de "Salvar" gera um `loteId` (cuid) comum compartilhado pelas N linhas daquele save, para a UI agrupar visualmente mesmo com reversão granular por linha. (5) **Model novo dedicado** `HistoricoAlteracaoCliente` (não reaproveita `logAlteracao`, que fica no schema desativado — sem gravação nova, sem remoção por ora). (6) `salvarAlteracoesGestao` (uma das 3 funções que gravavam no sistema antigo) é código morto confirmado por Scout (importada mas nunca chamada) — decisão: remover em vez de migrar.
**Alternativas rejeitadas:** Manter snapshot JSON completo (rejeitado — dificulta auditoria precisa e causa os falsos positivos de diff que o sistema antigo já tinha). FK `userId` com Cascade (rejeitado — contradiz o próprio propósito de `nomeUsuarioNaEpoca`, que existe para sobreviver a mudanças no usuário).
**Consequências:** `restaurarVersaoCliente` precisa de redesenho completo (não é só trocar de tabela) — vira uma reversão por campo que, ao reverter, também gera uma NOVA linha de histórico registrando a própria reversão (para não quebrar a cadeia de auditoria). Diff campo-a-campo precisa de comparação normalizada (`String(a ?? "").trim() === String(b ?? "").trim()`) para não poluir o log com falsas mudanças de tipo (`null` vs `""` etc). `modalLogAuditoria.tsx` precisa reescrita significativa: agrupar por `loteId`, exibir `nomeUsuarioNaEpoca`, trocar `confirm()` nativo por `AlertDialog` (padrão já usado em outros módulos como Extratos) na ação de reverter.

## Decisões

### 2026-06-19 — Extração de documentos via Apache Tika (primário) + pdf-parse v2 (fallback)
**Contexto:** Bibble e agentes Onyx precisavam ler PDFs e outros documentos. pdf-parse v1 havia sido substituído pela v2 que quebrou a API. Tika já estava instalado no servidor Onyx.
**Decisão:** `src/lib/bibble/tika.ts` centraliza toda extração de texto. Tika via `PUT http://192.168.35.113:9998/tika` é o primário; pdf-parse v2 (`new PDFParse({ data })`) é fallback apenas para PDFs quando Tika estiver indisponível.
**Alternativas rejeitadas:** Manter só pdf-parse v2 (suporta apenas PDF, sem DOCX/XLSX/PPTX); usar pdfjs-dist (já instalado mas complexo de usar em server-side Node.js).
**Consequências:** Suporte a PDF, DOCX, XLSX, PPTX, ODT, RTF, HTML, XML em uma única função. Dependência de rede interna (`192.168.35.113:9998`) — se o servidor Onyx cair, fallback garante PDFs. TIKA_SERVER_URL no .env.local. **Atualização:** em produção (Vercel), Tika e Onyx são acessados via Cloudflare Tunnel (`tika.alpha-comex.com`, `onyx.alpha-comex.com`) — IPs privados não funcionam da nuvem.

### 2026-06-19 — Memória de conversa: anexar conteúdo de PDF à mensagem persistida
**Contexto:** As IAs perdiam o contexto após responder — PDF analisado era esquecido na pergunta seguinte. Causa: só o texto digitado era salvo no histórico, não o conteúdo extraído do documento.
**Decisão:** A mensagem do usuário é persistida com o texto extraído dos arquivos anexado (`persistedContent`). A interface `Message` ganhou `fullContent` (vai para a IA) vs `content` (label curto na bolha). Histórico do Bibble usa janela por orçamento de caracteres proporcional ao `contextWindow`, não mais `slice(-10)` fixo. Onyx recebe `history` quando sua sessão zera.
**Alternativas rejeitadas:** Resumo persistente separado (mais econômico em tokens mas perde detalhes e mais complexo).
**Consequências:** IA reenxerga o documento em todo follow-up; janela de contexto das settings agora controla de fato a memória (proporcional). Custa mais tokens por turno. Aplica-se só ao Bibble — Onyx gerencia próprio contexto (não há janela configurável por agente pela API do Onyx).

### 2026-06-19 — Conhecimento unificado Bibble ⇄ Onyx via base compartilhada + tools, não RAG
**Contexto:** Agentes Onyx falhavam ao perguntar sobre processos internos; Bibble não acessava conhecimento do Onyx. Documentação de processos = dados vivos no banco, não PDFs estáticos.
**Decisão:** `src/lib/shared/painelalpha-knowledge.ts` é fonte única de verdade dos processos/vocabulário, injetada no system-prompt do Bibble E no system-knowledge dos agentes Onyx. Para dados vivos, usam-se tools em tempo real (Onyx via `AGENT_TOOLS` registry já existente; Bibble ganhou `consultar_base_onyx` via `askOnyxOneShot`).
**Alternativas rejeitadas:** RAG vetorizado / Knowledge Graph / Pinecone (over-engineering — Onyx já é RAG nativo; vetor de dados vivos desatualiza no segundo seguinte).
**Consequências:** Atualizar um processo em `painelalpha-knowledge.ts` propaga às duas IAs. `consultar_base_onyx` é exclusiva do Bibble (não no AGENT_TOOLS) para evitar loop. Base inicial inferida do código — exige revisão humana dos processos reais.

### 2026-06-26 — Identidade Onyx por usuário via token_onyx (PAT no banco)
**Contexto:** Cada usuário do Painel deveria falar com o Onyx como ele mesmo, não pela conta de serviço admin. Onyx não tem SSO configurado com o Painel.
**Decisão:** Campo `token_onyx String?` (nullable) em `usuarios`. Helper `getUserOnyxToken` resolve pelo id da sessão; client Onyx usa esse token quando presente, senão cai no PAT de serviço (ONYX_API_KEY). Aplicado a chat + todas as operações de agente. Token NUNCA volta ao client (só booleano `tem_token_onyx`); edição só admin/CEO.
**Alternativas rejeitadas:** SSO/OAuth (mais seguro/correto, mas é infra no servidor Onyx — fora do escopo do código do Painel).
**Consequências:** Provado real (Onyx /api/me + owner do agente = usuário certo). Tokens são credenciais no banco — exigem cuidado (já corrigido vazamento em get-user.ts). IMPORTANTE: app usa Turso direto via adapter (não dev.db) — mudanças de schema exigem ALTER TABLE manual no Turso.

### 2026-06-26 — Onyx como fonte de verdade do histórico de conversas com agente
**Contexto:** Imagens (enviadas e geradas) sumiam ao recarregar — histórico local (Prisma) só guardava texto. Onyx já persiste texto + anexos por mensagem.
**Decisão:** Conversas com agente Onyx leem o histórico do Onyx (`GET /chat/get-chat-session/{id}`) via rota `/api/onyx/session/[id]`. Salva-se só o `onyxSessionId` na BibbleSession. Conversas Bibble/Ollama seguem no histórico local.
**Alternativas rejeitadas:** Persistir anexos no Prisma (duplicaria o que o Onyx já faz; risco de dessincronizar).
**Consequências:** Conversa volta completa com imagens ao reabrir. Depende do Onyx estar no ar. Lightbox de imagem DEVE usar createPortal (backdrop-filter da bolha prende position:fixed). Upload de imagem usa `/api/user/projects/file/upload` com `user_file_id` no descriptor (o antigo `/api/chat/file` dá 307).

### 2026-07-02 — Pipeline de Extratos Bancários: Tika puro (OCR) + 1 agente único (Organizador)
**Contexto:** O fluxo anterior usava Tika só pra extrair texto bruto, depois encadeava 2 agentes Onyx de IA (Extrator #25 → Normalizador #26) pra interpretar e padronizar. O usuário criou um agente novo "Organizador de Extratos Bancários" (Onyx ID 32) pra assumir sozinho o trabalho de interpretação, e pediu explicitamente pra remover a cadeia dupla. Os agentes 25 e 26 foram deletados do Onyx.
**Decisão:** `src/lib/onyx/extrato-agents.ts` agora faz só 2 passos: (1) Tika extrai o texto bruto do PDF via `extractTextFromBuffer` — sem nenhuma IA envolvida; (2) o texto bruto vai para o agente único `AGENT_ORGANIZADOR_ID` (env `ONYX_AGENT_ORGANIZADOR_ID`, default `32`) via `PROMPT_ORGANIZACAO`, que devolve direto o JSON final `[{data, descricao, valor}]`. `PROMPT_EXTRACAO`/`PROMPT_NORMALIZACAO` e as constantes dos agentes 25/26 foram removidos.
**Alternativas rejeitadas:** Manter os 2 agentes e só trocar os IDs (rejeitado pelo usuário — ele quer 1 agente só, mais simples e barato).
**Consequências:** Menos uma chamada de rede/IA por extrato processado (mais rápido, mais barato). O agente Organizador agora carrega sozinho toda a responsabilidade de extração+normalização — se o texto do Tika vier muito longo (PDF com muitas páginas), vale monitorar se o agente único aguenta o contexto sem degradar. Contrato de saída pro frontend (`ModalUploadExtrato.tsx`, `SalvarTransacoesLote`) não mudou. **Atualização 2026-07-02:** implementação real revelou que o modelo qwen3 do agente 32 não processa prompts grandes de forma confiável (aborta reasoning sem responder) — resolvido dividindo o texto em chunks de ~3500 chars (`dividirEmChunks`) processados sequencialmente, com deduplicação por `data|descricao|valor` no agregado final (chunks adjacentes podem repetir a mesma linha na fronteira do corte). Ver `known-errors.md` para detalhes.

### 2026-07-02 — OCR fallback via PDF24 (Cross Service Solutions) para PDFs sem texto extraível
**Contexto:** PDFs de imagem/scan (sem camada de texto nativa — ex: gerados por ferramentas de recorte/split que rasterizam páginas) fazem tanto Tika quanto pdf-parse retornarem texto vazio ou insuficiente. Nenhum dos dois faz OCR de verdade; só extraem texto que já existe como camada digital no PDF. Usuário obteve acesso a uma API de OCR real (PDF24/Cross Service Solutions, Tesseract-based).
**Decisão:** `src/lib/bibble/pdf24-ocr.ts` (novo módulo) implementa o ciclo assíncrono da API (criar job → polling até `output.files` preencher → baixar PDF processado). `src/lib/bibble/tika.ts` aciona esse módulo como 3º estágio de fallback: só quando Tika E pdf-parse não renderem texto suficiente (<20 chars úteis, descontando marcadores de página) E o arquivo for PDF E `PDF24_OCR_API_URL`/`PDF24_OCR_API_KEY` estiverem configurados. O PDF resultante do OCR é reprocessado pelo Tika (agora com camada de texto) para extrair o texto final. `source` do retorno de `extractTextFromBuffer`/`extractTextFromUrl` ganhou o valor `"pdf24-ocr"`.
**Alternativas rejeitadas:** Substituir o Tika totalmente pela PDF24 (rejeitado — Tika é síncrono e rápido para PDFs com texto nativo, que é o caso comum; PDF24 é assíncrona com polling, boa só como último recurso).
**Consequências:** Tika continua sendo o caminho rápido padrão. PDF24 só entra em ação (mais lento — job assíncrono) quando o PDF genuinamente não tem texto extraível. Sem `PDF24_OCR_API_URL`/`PDF24_OCR_API_KEY` configurados, o comportamento é idêntico a antes. **Atualização 2026-07-02:** testado contra a API real — endpoint correto era `/api/67` (67 = id da "solução" PDF OCR na plataforma, não `/api/` puro), critério de conclusão corrigido (`output.files.length > 0`, não `output !== null`), timeout de polling ajustado para 8 min (job real de 3 páginas de scan levou pouco mais de 8 min). Ver `known-errors.md` para detalhes completos.

### 2026-07-02 — Extratos bancários: agente Onyx substituído por parsers determinísticos por banco
**Contexto:** O agente único "Organizador de Extratos Bancários" (Onyx ID 32) foi testado com um extrato real de 48 transações e retornou só 40 — perdeu 8 (16,7%) sem padrão de erro claro, mesmo após ajustes de chunking/prompt/retry. Layout de extrato bancário é uma tabela ESTRUTURADA e ESTÁVEL por banco (Bradesco sempre formata igual, Nubank sempre formata igual, etc) — não é um problema que precise de "inteligência" de LLM, precisa de regra determinística correta.
**Decisão:** Removida a dependência do agente Onyx do fluxo principal de extratos. Novo pipeline em `src/lib/extrato/parsers/`: um `ParserExtrato` (interface com `parse(texto): TransacaoNormalizada[]`) por banco do catálogo (`ModalBanco.tsx`), registry em `parsers/index.ts` (`obterParser(bancoId)`). `src/app/api/onyx/extrato/route.ts` busca o tipo do banco via `BancosVinculados.bancoId` (usando o id numérico recebido do form) e aplica o parser certo sobre o texto já extraído por Tika/pdf-parse/PDF24 (pipeline de extração de texto inalterado). Só o parser do **Bradesco** é real, testado contra amostra confirmada (8/8 transações extraídas corretamente num teste manual). Os outros 14 bancos usam um `parserGenerico` (heurística "melhor esforço": linha com data DD/MM/YYYY + valor monetário BR) até haver amostra real de cada um — arquivos individuais por banco (`nubank.ts`, `itau.ts` etc) já existem prontos para receber lógica dedicada sem afetar os demais.
**Alternativas rejeitadas:** Manter o agente e tentar mais ajustes de prompt/chunking (rejeitado pelo usuário — layout de tabela fixo não deveria depender de inferência de IA); um único parser genérico sem diferenciação por banco (rejeitado — bancos diferentes têm layout de coluna genuinamente diferente, um regex só não escala).
**Consequências:** Zero custo de IA nessa etapa, zero variação entre execuções (determinístico). `src/lib/onyx/extrato-agents.ts` ficou órfão (mantido no repo sem uso, para rollback fácil se necessário — não deletado). Parsers dos 14 bancos "melhor esforço" vão precisar de ajuste quando testados com extrato real de cada um — usuário está ciente. Limitação conhecida do parser Bradesco: a primeira linha de cada dia pode confundir valor de transação com saldo/total quando o texto do OCR é ambíguo (só 1 caso observado até agora, documentado no código).
**REVERTIDO em 2026-07-02** — ver decisão abaixo.

### 2026-07-02 — Extratos bancários: revertido para agente Onyx, mas processando por PÁGINA REAL do PDF (não regex, não chunk por tamanho)
**Contexto:** A tentativa de parsers determinísticos (regex por banco, decisão acima) foi abandonada pelo usuário — layout de extrato varia demais entre bancos/versões, regex fixo quebra fácil e não escala. Usuário pediu para voltar ao agente de IA, mas resolvendo a causa raiz do problema original (perder 8/48 transações): o chunking por tamanho de caractere (~3500 chars) cortava linhas de transação exatamente na fronteira do corte.
**Decisão:** `src/lib/onyx/extrato-agents.ts` voltou a usar o Agente Organizador (Onyx ID 32), mas a divisão do texto agora é por **página real do PDF** via `pdf-parse` (`PDFParse.getText()` → `result.pages: Array<{num, text}>`, extração nativa por página, não corte arbitrário de string). **Consequências:** Testado com o PDF real de 18 páginas do usuário: `pdf-parse` extraiu 18/18 páginas com texto útil, média de ~2000 chars por página (bem menor que os 3500 do chunking anterior, e muito menor que os ~37k do texto inteiro) — deve reduzir bastante o risco do modelo qwen3 abortar reasoning por volume de texto. `src/lib/extrato/parsers/*` ficou órfão (mantido para rollback, não deletado). Ainda não testado end-to-end via app real com este ajuste — próximo passo é o usuário testar e confirmar se as 48 transações batem agora.

**Consequências:** `formPorCard` (estado por card em `modalDados.tsx`) ganha `formaPagamento`/`valorContrato`/`closerNome`. **Decisão confirmada com o usuário:** ao editar esses 3 campos (mesmo quando há contrato do Metas vinculado), salva-se SEMPRE em `clientes.formaPagamento`/`valorContrato`/`closerNome` (NUNCA no `ContratoComercial` do Metas). A partir do momento em que o registro tiver esses campos próprios preenchidos (editados manualmente), a exibição do card passa a PRIORIZAR o dado próprio de `clientes` sobre o dado do Metas — inverte a prioridade de exibição atual (hoje: Metas > próprio > vazio; nova prioridade: próprio (se editado) > Metas > vazio). Fonte de referência: já existem em `.bibble/memory/architecture.md` os campos `municipio`/`formaPagamento`/`valorContrato`/`closerNome` em `clientes`, adicionados na mesma sessão.

### 2026-07-13 — Painel de Metas: bug real de "Forma de Pagamento" custom nunca era salva (afetava exibição no CS&NPS)
**Contexto:** Ao revisar o dropdown de Forma de Pagamento nos cards do CS&NPS, usuário reportou que a opção "outro" no Painel de Metas (`ModalGerenciamentoLeads.tsx`) sempre exibia só "Outro" no CS&NPS, nunca o texto que o comercial digitou. Investigação encontrou bug real no formulário do Metas: `formaPagamentoFinal = mostraFormaPagCustom ? "OUTRO" : formaPagamento` — a string fixa `"OUTRO"` era enviada ao backend, e o texto digitado em `formaPagamentoCustom` nunca entrava no payload (era só exibido localmente, depois descartado). O Zod em `ContratoComercial.ts` (`CriarContratoSchema`/`AtualizarContratoSchema`) reforçava isso com `formaPagamento: z.enum([...4 valores fixos, incluindo "OUTRO"])`, mesmo o schema do Prisma (`ContratoComercial.formaPagamento`) sendo `String` livre, sem constraint de enum no banco.
**Decisão:** Corrigido na origem (Metas), não no CS&NPS. (1) `formaPagamentoFinal` agora usa `formaPagamentoCustom.trim()` em vez de `"OUTRO"` fixo. (2) Zod dos dois schemas trocado de `z.enum([...])` para `z.string().min(1)` (mesmo padrão já usado em `canalAquisicao`, que também é texto livre validado só por tamanho mínimo). (3) `formaPagamentoCustom` agora é inicializado com o valor salvo (`initialData.formaPagamento`) quando `isCustomPag` for true, para a edição de um contrato existente recarregar o texto customizado. O CS&NPS (`formas-pagamento.ts`, `formatarFormaPagamento`) **não precisou de nenhuma mudança** — já tinha fallback `FORMAS_LABEL[valor] ?? valor` que exibe texto livre corretamente, só nunca recebia o texto real por causa do bug na origem.
**Consequências:** Contratos já salvos no banco ANTES desta correção continuam com a string literal `"OUTRO"` gravada (dado histórico perdido, o texto original nunca existiu no banco) — não há como recuperar retroativamente. Só contratos criados/editados a partir de agora gravam o texto real.

### 2026-07-10 — Frente 1 (pós-Onda 5): expansão de 10 para 24 tipos de componente, unificação por campo de variante
**Contexto:** Usuário testou o produto e reportou que a entrega estava muito aquém do prompt original (~400 linhas, pedia dezenas de tipos de componente — Dados, Business, IA, Comex). Confirmou querer a expansão completa E aprovou instalar `@xyflow/react` para os tipos de grafo.
**Decisão:** Em vez de criar um tipo dedicado para cada variação pedida no prompt original (organograma/fluxograma/mapa mental separados, SWOT/matriz2x2/pirâmide/funil separados, Colunas/Stack/Flex separados), adotou-se **unificação por campo de variante**: um único schema Zod com um campo (`layout`/`estilo`/`formato`) que muda a aparência/comportamento. Aplicado em `container` (layout: grid/flex-row/flex-col/stack), `grafo` (estilo: organograma/fluxograma/mapamental, via `@xyflow/react@12.11.2`, nova dependência), `diagrama` (formato: swot/matriz2x2/piramide/funil). Também se decidiu **estender schema existente em vez de criar tipo novo** quando o conceito já era coberto por um componente existente: mapas de rotas/comex viraram um campo `rotas[]` no `globoComponenteSchema` (Onda 4) em vez de um tipo `mapaRotas` dedicado. Incoterms/NCM/Radar Siscomex/Mercadorias do prompt original **não** viraram tipos — são casos de uso de `card`/`tabela`/`texto` já existentes.
**Alternativas rejeitadas:** Criar 3-4 schemas quase idênticos por conceito (rejeitado — duplicação que Lens sempre marca, sem ganho real já que a única diferença real entre os "3 tipos" em cada caso é a aparência padrão, não a estrutura de dados); SVG inline via `dangerouslySetInnerHTML` (rejeitado por segurança — SVG aceito só via URL, mesmo padrão do tipo `imagem`, evita todo o problema de sanitização).
**Consequências:** Biblioteca de componentes cresceu de 10 para 24 tipos sem crescer proporcionalmente em número de schemas/arquivos de render — o padrão de unificação por variante deve ser o primeiro caminho considerado sempre que o usuário pedir "vários tipos parecidos" no futuro (Frente 2, motor de IA, ou expansões futuras). A duplicação de lógica de renderização de containers entre `RenderComponente.tsx` e `ComponenteNoCanvas.tsx` (já era dívida técnica desde a Onda 2) cresceu em complexidade com o novo tipo `container` — ver `components.md`/`integration-points.md`.

### 2026-08-04 — Alpha Metas: "Justificativa de Meta" — modelo de vigente + histórico imutável, sem `@@unique`
**Contexto:** Usuário pediu upload de PDF de justificativa mensal, restrito a Admin/TI/CEO/Líder Comercial, onde um novo upload "sobrescreve" o vigente do mês/ano, mas o histórico precisa preservar TODAS as versões anteriores (clicáveis, não só metadado).
**Decisão:** Rejeitado o padrão óbvio de `@@unique([mes, ano])` + `update()` (que fisicamente sobrescreveria a linha, perdendo o arquivo antigo). Em vez disso, `JustificativaMeta` nunca tem constraint de unicidade em `mes+ano` — cada upload é sempre um `create()` novo. "Vigente" é sempre DERIVADO (`findFirst({ where: {mes, ano}, orderBy: {createdAt: "desc"} })`), nunca um campo `ativo`/flag armazenado. "Sobrescrever" é puramente semântico (deixa de ser o mais recente), nunca físico (nada é deletado ou editado).
**Alternativas rejeitadas:** `@@unique([mes,ano])` + campo `historicoJson` acumulando URLs antigas dentro do mesmo registro (rejeitado — dificulta querying/paginação do histórico, e a "linha vigente" vira uma mistura de responsabilidades); soft-delete com `versao`/`ativo: boolean` (rejeitado — redundante, já que `orderBy: createdAt desc` resolve a mesma pergunta sem precisar manter um campo sincronizado).
**Consequências:** Padrão reutilizável para qualquer feature futura do tipo "documento vigente por período com histórico completo" (ver `MetaUsuario`/`MetaEquipe` para o padrão OPOSTO — vigente único por período, sem histórico — usado quando o histórico não importa). Nunca aplicar `@@unique` num campo de período quando a intenção é também preservar histórico.

### 2026-08-04 — Alpha Metas: botão sempre visível + autorização só no conteúdo do modal (padrão alternativo ao "botão condicional")
**Contexto:** O padrão pré-existente do módulo Metas (botão "Configurar Metas") só renderiza o botão para quem tem a permissão — `{(isAdmin || role === 'CEO' || role === 'Lider Comercial') && <button>...}`. Para "Justificativa de Meta", a intenção de produto era diferente: TODO o time do Comercial precisa poder abrir e VER o documento, só um subconjunto pode fazer upload.
**Decisão:** O botão "Justificativa de Meta" é renderizado incondicionalmente (sem checagem de role no JSX do botão); a prop `podeGerenciar` (mesma expressão de role) é passada ao modal, que decide internamente se mostra o formulário de upload ou só o preview de leitura. A autorização REAL de escrita continua 100% no backend (Server Action + Route Handler), independente do que o client decide renderizar.
**Alternativas rejeitadas:** Replicar o padrão condicional existente e criar dois botões diferentes ("Ver Justificativa" para todos + "Gerenciar Justificativa" só para quem gerencia) — rejeitado por criar 2 pontos de entrada para o mesmo dado, mais superfície de UI sem necessidade real.
**Consequências:** Este é o padrão a seguir sempre que a intenção de produto for "todo mundo pode SABER que a feature existe e VER o resultado, só alguns podem EDITAR" — diferente de features onde a própria existência deve ficar oculta de quem não tem acesso (aí sim o padrão condicional do botão "Configurar Metas" é o correto). Não confundir os dois casos ao desenhar blueprint de features futuras.

### 2026-08-04 — Alpha Metas: Blob Store dedicado com `access: "private"` para documento interno não-público
**Contexto:** Ao decidir onde armazenar o PDF de justificativa de meta, havia a opção de reaproveitar o `BLOB_READ_WRITE_TOKEN` genérico (usado por Apresentações/Chat/Avatar) ou criar um token dedicado como já existe para Comissões/Holerites/Blueprint/Skills.
**Decisão:** Token dedicado `METAS_READ_WRITE_TOKEN`, `access: "private"` no `put()`. Reforça o padrão já estabelecido: qualquer documento com controle de acesso por role/permissão (não um asset público tipo imagem de apresentação) ganha Blob Store próprio, nunca reaproveita o token genérico. Leitura sempre passa por uma Route Handler autenticada que faz `get()` do Blob e retorna o stream — a URL do Blob nunca é exposta diretamente ao client.
**Alternativas rejeitadas:** `access: "public"` com URL do Blob armazenada e servida direto ao client (rejeitado — vazaria a URL do PDF para qualquer pessoa que a obtivesse, sem re-checagem de permissão a cada acesso); reaproveitar `BLOB_READ_WRITE_TOKEN` genérico (rejeitado — mistura documentos com controle de acesso diferente sob o mesmo token, dificultando auditoria/rotação futura por domínio).
**Consequências:** Padrão a seguir para qualquer feature futura de upload de documento restrito por role: token de Blob Store dedicado + `access: "private"` + Route Handler de leitura autenticada, nunca URL pública direta.
