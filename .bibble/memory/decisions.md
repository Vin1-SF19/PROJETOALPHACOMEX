## Decisões

### 2026-06-19 — Extração de documentos via Apache Tika (primário) + pdf-parse v2 (fallback)
**Contexto:** Bibble e agentes Onyx precisavam ler PDFs e outros documentos. pdf-parse v1 havia sido substituído pela v2 que quebrou a API. Tika já estava instalado no servidor Onyx.
**Decisão:** `src/lib/bibble/tika.ts` centraliza toda extração de texto. Tika via `PUT http://192.168.35.113:9998/tika` é o primário; pdf-parse v2 (`new PDFParse({ data })`) é fallback apenas para PDFs quando Tika estiver indisponível.
**Alternativas rejeitadas:** Manter só pdf-parse v2 (suporta apenas PDF, sem DOCX/XLSX/PPTX); usar pdfjs-dist (já instalado mas complexo de usar em server-side Node.js).
**Consequências:** Suporte a PDF, DOCX, XLSX, PPTX, ODT, RTF, HTML, XML em uma única função. Dependência de rede interna (`192.168.35.113:9998`) — se o servidor Onyx cair, fallback garante PDFs. TIKA_SERVER_URL no .env.local. **Atualização:** em produção (Vercel), Tika e Onyx são acessados via Cloudflare Tunnel (`tika.alpha-comex.com`, `onyx.alpha-comex.com`) — IPs privados não funcionam da nuvem.

### 2026-06-19 — Memória de conversa: anexar conteúdo de PDF à mensagem persistida
**Contexto:** As IAs perdiam o contexto após responder — PDF analisado era esquecido na pergunta seguinte. Causa: só o texto digitado era salvo no histórico, não o conteúdo extraído do documento.
**Decisão:** A mensagem do usuário é persistida com o texto extraído dos arquivos anexado (`persistedContent`). A interface `Message` ganhou `fullContent` (vai para a IA) vs `content` (label curto na bolha). Histórico do Bibble usa janela por orçamento de caracteres proporcional ao `contextWindow`, não mais `slice(-10)` fixo. Onyx recebe `history` quando sua sessão zera.
**Alternativas rejeitadas:** Resumo persistente separado (mais econômico em tokens mas perde detalhes e mais complexo).
**Consequências:** IA reenxerga o documento em todo follow-up; janela de contexto das settings agora controla de fato a memória (proporcional). Custa mais tokens por turno. Aplica-se só ao Bibble — Onyx gerencia próprio contexto (não há janela configurável por agente pela API do Onyx).

### 2026-06-19 — Conhecimento unificado Bibble ⇄ Onyx via base compartilhada + tools, não RAG
**Contexto:** Agentes Onyx falhavam ao perguntar sobre processos internos; Bibble não acessava conhecimento do Onyx. Documentação de processos = dados vivos no banco, não PDFs estáticos.
**Decisão:** `src/lib/shared/painelalpha-knowledge.ts` é fonte única de verdade dos processos/vocabulário, injetada no system-prompt do Bibble E no system-knowledge dos agentes Onyx. Para dados vivos, usam-se tools em tempo real (Onyx via `AGENT_TOOLS` registry já existente; Bibble ganhou `consultar_base_onyx` via `askOnyxOneShot`).
**Alternativas rejeitadas:** RAG vetorizado / Knowledge Graph / Pinecone (over-engineering — Onyx já é RAG nativo; vetor de dados vivos desatualiza no segundo seguinte).
**Consequências:** Atualizar um processo em `painelalpha-knowledge.ts` propaga às duas IAs. `consultar_base_onyx` é exclusiva do Bibble (não no AGENT_TOOLS) para evitar loop. Base inicial inferida do código — exige revisão humana dos processos reais.

### 2026-06-26 — Identidade Onyx por usuário via token_onyx (PAT no banco)
**Contexto:** Cada usuário do Painel deveria falar com o Onyx como ele mesmo, não pela conta de serviço admin. Onyx não tem SSO configurado com o Painel.
**Decisão:** Campo `token_onyx String?` (nullable) em `usuarios`. Helper `getUserOnyxToken` resolve pelo id da sessão; client Onyx usa esse token quando presente, senão cai no PAT de serviço (ONYX_API_KEY). Aplicado a chat + todas as operações de agente. Token NUNCA volta ao client (só booleano `tem_token_onyx`); edição só admin/CEO.
**Alternativas rejeitadas:** SSO/OAuth (mais seguro/correto, mas é infra no servidor Onyx — fora do escopo do código do Painel).
**Consequências:** Provado real (Onyx /api/me + owner do agente = usuário certo). Tokens são credenciais no banco — exigem cuidado (já corrigido vazamento em get-user.ts). IMPORTANTE: app usa Turso direto via adapter (não dev.db) — mudanças de schema exigem ALTER TABLE manual no Turso.

### 2026-06-26 — Onyx como fonte de verdade do histórico de conversas com agente
**Contexto:** Imagens (enviadas e geradas) sumiam ao recarregar — histórico local (Prisma) só guardava texto. Onyx já persiste texto + anexos por mensagem.
**Decisão:** Conversas com agente Onyx leem o histórico do Onyx (`GET /chat/get-chat-session/{id}`) via rota `/api/onyx/session/[id]`. Salva-se só o `onyxSessionId` na BibbleSession. Conversas Bibble/Ollama seguem no histórico local.
**Alternativas rejeitadas:** Persistir anexos no Prisma (duplicaria o que o Onyx já faz; risco de dessincronizar).
**Consequências:** Conversa volta completa com imagens ao reabrir. Depende do Onyx estar no ar. Lightbox de imagem DEVE usar createPortal (backdrop-filter da bolha prende position:fixed). Upload de imagem usa `/api/user/projects/file/upload` com `user_file_id` no descriptor (o antigo `/api/chat/file` dá 307).

### 2026-07-02 — Pipeline de Extratos Bancários: Tika puro (OCR) + 1 agente único (Organizador)
**Contexto:** O fluxo anterior usava Tika só pra extrair texto bruto, depois encadeava 2 agentes Onyx de IA (Extrator #25 → Normalizador #26) pra interpretar e padronizar. O usuário criou um agente novo "Organizador de Extratos Bancários" (Onyx ID 32) pra assumir sozinho o trabalho de interpretação, e pediu explicitamente pra remover a cadeia dupla. Os agentes 25 e 26 foram deletados do Onyx.
**Decisão:** `src/lib/onyx/extrato-agents.ts` agora faz só 2 passos: (1) Tika extrai o texto bruto do PDF via `extractTextFromBuffer` — sem nenhuma IA envolvida; (2) o texto bruto vai para o agente único `AGENT_ORGANIZADOR_ID` (env `ONYX_AGENT_ORGANIZADOR_ID`, default `32`) via `PROMPT_ORGANIZACAO`, que devolve direto o JSON final `[{data, descricao, valor}]`. `PROMPT_EXTRACAO`/`PROMPT_NORMALIZACAO` e as constantes dos agentes 25/26 foram removidos.
**Alternativas rejeitadas:** Manter os 2 agentes e só trocar os IDs (rejeitado pelo usuário — ele quer 1 agente só, mais simples e barato).
**Consequências:** Menos uma chamada de rede/IA por extrato processado (mais rápido, mais barato). O agente Organizador agora carrega sozinho toda a responsabilidade de extração+normalização — se o texto do Tika vier muito longo (PDF com muitas páginas), vale monitorar se o agente único aguenta o contexto sem degradar. Contrato de saída pro frontend (`ModalUploadExtrato.tsx`, `SalvarTransacoesLote`) não mudou. **Atualização 2026-07-02:** implementação real revelou que o modelo qwen3 do agente 32 não processa prompts grandes de forma confiável (aborta reasoning sem responder) — resolvido dividindo o texto em chunks de ~3500 chars (`dividirEmChunks`) processados sequencialmente, com deduplicação por `data|descricao|valor` no agregado final (chunks adjacentes podem repetir a mesma linha na fronteira do corte). Ver `known-errors.md` para detalhes.

### 2026-07-02 — OCR fallback via PDF24 (Cross Service Solutions) para PDFs sem texto extraível
**Contexto:** PDFs de imagem/scan (sem camada de texto nativa — ex: gerados por ferramentas de recorte/split que rasterizam páginas) fazem tanto Tika quanto pdf-parse retornarem texto vazio ou insuficiente. Nenhum dos dois faz OCR de verdade; só extraem texto que já existe como camada digital no PDF. Usuário obteve acesso a uma API de OCR real (PDF24/Cross Service Solutions, Tesseract-based).
**Decisão:** `src/lib/bibble/pdf24-ocr.ts` (novo módulo) implementa o ciclo assíncrono da API (criar job → polling até `output.files` preencher → baixar PDF processado). `src/lib/bibble/tika.ts` aciona esse módulo como 3º estágio de fallback: só quando Tika E pdf-parse não renderem texto suficiente (<20 chars úteis, descontando marcadores de página) E o arquivo for PDF E `PDF24_OCR_API_URL`/`PDF24_OCR_API_KEY` estiverem configurados. O PDF resultante do OCR é reprocessado pelo Tika (agora com camada de texto) para extrair o texto final. `source` do retorno de `extractTextFromBuffer`/`extractTextFromUrl` ganhou o valor `"pdf24-ocr"`.
**Alternativas rejeitadas:** Substituir o Tika totalmente pela PDF24 (rejeitado — Tika é síncrono e rápido para PDFs com texto nativo, que é o caso comum; PDF24 é assíncrona com polling, boa só como último recurso).
**Consequências:** Tika continua sendo o caminho rápido padrão. PDF24 só entra em ação (mais lento — job assíncrono) quando o PDF genuinamente não tem texto extraível. Sem `PDF24_OCR_API_URL`/`PDF24_OCR_API_KEY` configurados, o comportamento é idêntico a antes. **Atualização 2026-07-02:** testado contra a API real — endpoint correto era `/api/67` (67 = id da "solução" PDF OCR na plataforma, não `/api/` puro), critério de conclusão corrigido (`output.files.length > 0`, não `output !== null`), timeout de polling ajustado para 8 min (job real de 3 páginas de scan levou pouco mais de 8 min). Ver `known-errors.md` para detalhes completos.

### 2026-07-02 — Extratos bancários: agente Onyx substituído por parsers determinísticos por banco
**Contexto:** O agente único "Organizador de Extratos Bancários" (Onyx ID 32) foi testado com um extrato real de 48 transações e retornou só 40 — perdeu 8 (16,7%) sem padrão de erro claro, mesmo após ajustes de chunking/prompt/retry. Layout de extrato bancário é uma tabela ESTRUTURADA e ESTÁVEL por banco (Bradesco sempre formata igual, Nubank sempre formata igual, etc) — não é um problema que precise de "inteligência" de LLM, precisa de regra determinística correta.
**Decisão:** Removida a dependência do agente Onyx do fluxo principal de extratos. Novo pipeline em `src/lib/extrato/parsers/`: um `ParserExtrato` (interface com `parse(texto): TransacaoNormalizada[]`) por banco do catálogo (`ModalBanco.tsx`), registry em `parsers/index.ts` (`obterParser(bancoId)`). `src/app/api/onyx/extrato/route.ts` busca o tipo do banco via `BancosVinculados.bancoId` (usando o id numérico recebido do form) e aplica o parser certo sobre o texto já extraído por Tika/pdf-parse/PDF24 (pipeline de extração de texto inalterado). Só o parser do **Bradesco** é real, testado contra amostra confirmada (8/8 transações extraídas corretamente num teste manual). Os outros 14 bancos usam um `parserGenerico` (heurística "melhor esforço": linha com data DD/MM/YYYY + valor monetário BR) até haver amostra real de cada um — arquivos individuais por banco (`nubank.ts`, `itau.ts` etc) já existem prontos para receber lógica dedicada sem afetar os demais.
**Alternativas rejeitadas:** Manter o agente e tentar mais ajustes de prompt/chunking (rejeitado pelo usuário — layout de tabela fixo não deveria depender de inferência de IA); um único parser genérico sem diferenciação por banco (rejeitado — bancos diferentes têm layout de coluna genuinamente diferente, um regex só não escala).
**Consequências:** Zero custo de IA nessa etapa, zero variação entre execuções (determinístico). `src/lib/onyx/extrato-agents.ts` ficou órfão (mantido no repo sem uso, para rollback fácil se necessário — não deletado). Parsers dos 14 bancos "melhor esforço" vão precisar de ajuste quando testados com extrato real de cada um — usuário está ciente. Limitação conhecida do parser Bradesco: a primeira linha de cada dia pode confundir valor de transação com saldo/total quando o texto do OCR é ambíguo (só 1 caso observado até agora, documentado no código).
**REVERTIDO em 2026-07-02** — ver decisão abaixo.

### 2026-07-02 — Extratos bancários: revertido para agente Onyx, mas processando por PÁGINA REAL do PDF (não regex, não chunk por tamanho)
**Contexto:** A tentativa de parsers determinísticos (regex por banco, decisão acima) foi abandonada pelo usuário — layout de extrato varia demais entre bancos/versões, regex fixo quebra fácil e não escala. Usuário pediu para voltar ao agente de IA, mas resolvendo a causa raiz do problema original (perder 8/48 transações): o chunking por tamanho de caractere (~3500 chars) cortava linhas de transação exatamente na fronteira do corte.
**Decisão:** `src/lib/onyx/extrato-agents.ts` voltou a usar o Agente Organizador (Onyx ID 32), mas a divisão do texto agora é por **página real do PDF** via `pdf-parse` (`PDFParse.getText()` → `result.pages: Array<{num, text}>`, extração nativa por página, não corte arbitrário de string). Cada página vira 1 chamada ao agente (`organizarPagina`), evitando cortar uma transação no meio — extratos não quebram uma linha de lançamento entre páginas. Se nenhuma página tiver texto útil (PDF de scan/imagem), aciona `ocrViaPdf24` como fallback e tenta a extração por página de novo no PDF resultante do OCR. `src/app/api/onyx/extrato/route.ts` voltou a chamar `processarExtratoPorAgentes` (removida a dependência de `BancosVinculados`/Prisma que os parsers precisavam).
**Alternativas rejeitadas:** Parsers determinísticos por banco (rejeitado — não escala, quebra a cada variação); detecção dinâmica de colunas via posição X/Y no PDF ou via cabeçalho (consideradas, não escolhidas — usuário preferiu voltar à IA resolvendo o bug real).
**Consequências:** Testado com o PDF real de 18 páginas do usuário: `pdf-parse` extraiu 18/18 páginas com texto útil, média de ~2000 chars por página (bem menor que os 3500 do chunking anterior, e muito menor que os ~37k do texto inteiro) — deve reduzir bastante o risco do modelo qwen3 abortar reasoning por volume de texto. `src/lib/extrato/parsers/*` ficou órfão (mantido para rollback, não deletado). Ainda não testado end-to-end via app real com este ajuste — próximo passo é o usuário testar e confirmar se as 48 transações batem agora.

### 2026-07-02 — Extratos bancários: resiliência por página + reprocessamento manual
**Contexto:** Usuário relatou 30 minutos processando um PDF de 18 páginas e a página 9 falhar — o loop em `processarExtratoPorAgentes` abortava inteiro na primeira falha de página (sem try/catch), jogando fora o trabalho das páginas 1-8 e 10-18 que já tinham processado com sucesso.
**Decisão:** O loop de páginas agora captura falha por página (try/catch), acumula em `paginasComErro: PaginaComErro[]` (com o texto da página, pra reprocessar sem re-upload do PDF) e **continua** processando as demais. `POST /api/onyx/extrato` retorna `{ data: transacoes, paginasComErro }` mesmo com falhas parciais (não é mais erro fatal — só falha total se NENHUMA página tiver texto extraível). Novo endpoint `POST /api/onyx/extrato/reprocessar` recebe `{ paginas: PaginaComErro[] }` e roda `organizarPagina` (exportada) de novo só nelas, sem reler o PDF. `ModalUploadExtrato.tsx` acumula `paginasComErro` entre arquivos do lote, mostra banner amarelo com contagem + botão único "Reprocessar páginas com erro" na tela de review — reprocessa TODAS as páginas com falha de uma vez (decisão do usuário: não quis botão por página individual).
**Alternativas rejeitadas:** Botão de reprocessar por página individual (usuário preferiu 1 botão que tenta tudo de uma vez); re-extrair o PDF inteiro no reprocessamento (rejeitado — desperdiça trabalho já feito e é mais lento; o texto da página já vem na resposta original).
**Consequências:** Nenhuma falha pontual perde mais trabalho já concluído. Resposta JSON de `/api/onyx/extrato` fica um pouco maior quando há erro (carrega o texto das páginas problemáticas), aceitável (~2000 chars por página em média). `SalvarTransacoesLote`/fluxo de salvar não mudou — reprocessamento só alimenta o mesmo array antes de salvar.

### 2026-07-06 — Migration de schema no Turso remoto: `prisma db push` NÃO alcança o banco de produção
**Contexto:** Ao adicionar 7 colunas nullable em `PreCadastroParceiro` para o wizard de convite de parceiro, `npx prisma db push` rodou "com sucesso" mas silenciosamente só aplicou no SQLite local (`prisma/dev.db`) — o `datasource db` do schema usa `DATABASE_URL` (`file:./prisma/dev.db`), enquanto o app em runtime conecta ao Turso via `PrismaLibSql` adapter (`src/lib/prisma.ts`, lê `TURSO_DATABASE_URL`/`TURSO_AUTH_TOKEN`). São dois caminhos de conexão desacoplados: o Prisma CLI só enxerga o `datasource` do schema (local), nunca o adapter usado em runtime.
**Decisão:** Para aplicar mudança de schema no Turso de produção, rodar um script pontual em Node usando `@libsql/client/web` (mesmo pacote/transporte HTTP que `src/lib/prisma.ts` já usa) com `ALTER TABLE ... ADD COLUMN ...` direto, lendo `TURSO_DATABASE_URL`/`TURSO_AUTH_TOKEN` do `.env`. Script é criado na raiz do projeto (para resolver `@libsql/client` do `node_modules` local), executado uma vez, e apagado logo depois — nunca commitado. Sempre confirmar com `PRAGMA table_info(tabela)` antes/depois para garantir idempotência (script pode checar colunas existentes e pular as que já existem).
**Alternativas rejeitadas:** Instalar/usar `turso` CLI (não estava instalado na máquina, adicionaria dependência externa só para uma operação pontual); confiar que `prisma db push`/`migrate deploy` alcançariam o Turso (testado e confirmado que NÃO alcançam neste projeto, dado o adapter customizado).
**Consequências:** Toda sessão futura que precisar alterar `prisma/schema.prisma` DEVE, após `prisma generate`, replicar a mudança no Turso manualmente via este método (ou equivalente) — `prisma db push`/`migrate` sozinhos NÃO bastam neste projeto. Vault deve continuar sendo acionado antes de qualquer `ALTER TABLE` em produção, independente do mecanismo usado para aplicá-lo. Ver nota complementar em `known-errors.md`.

### 2026-07-06 — PIN de 4 dígitos protege a busca automática de CPF no convite (campo nullable, não default)
**Contexto:** A busca automática de CPF (InfoSimples) no wizard de convite de parceiro precisava de uma rota pública (sem `auth()`), mas isso exigia alguma proteção contra abuso — cada chamada à InfoSimples tem custo real. O usuário pediu um PIN de 4 dígitos gerado junto com o link, exibido só na hora da criação do convite.
**Decisão:** `ConviteParceiro.pin` é `String?` **nullable**, não `NOT NULL` nem `@default("0000")`. Vault classificou como a única opção segura de migration: `NOT NULL` sem default quebraria o `ALTER TABLE` em produção (tabela já tinha linhas); `@default("0000")` rodaria mas criaria um segredo previsível/hardcoded — pior que não ter PIN algum, porque parece proteção sem ser. Convites gerados ANTES desta feature ficam com `pin = null` e são **bloqueados explicitamente** de usar a busca automática (`/api/convite/consulta-cpf` retorna erro se `convite.pin` for null) — não recebem um passe livre.
**Alternativas rejeitadas:** `@default("0000")` (rejeitado por Vault — segredo previsível); reaproveitar a rota autenticada `ConsultaCpf/route.ts` (rejeitado — exige sessão, incompatível com fluxo público sem login).
**Consequências:** `gerarConvite` (`convites-parceiro.ts`) gera o PIN com `Math.random()` (não criptograficamente forte, mas o vetor de ataque prático é força bruta simples de 10 mil combinações, não previsibilidade do gerador). `listarConvites` NUNCA retorna o PIN — só aparece no retorno de `gerarConvite`, exibido uma vez em `ModalConvidarParceiro.tsx`.

### 2026-07-06 — RISCO ACEITO CONSCIENTEMENTE: sem rate-limit na consulta de CPF do convite
**Contexto:** Anubis auditou a nova rota `/api/convite/consulta-cpf` e encontrou uma falha real: não há contador de tentativas nem rate-limit. O PIN de 4 dígitos (10.000 combinações) pode ser quebrado por força bruta em minutos; mesmo com PIN correto, não há teto de quantas consultas pagas podem ser feitas no mesmo convite enquanto ele estiver `PENDENTE`. Isso é um vetor real de gasto financeiro ilimitado na conta InfoSimples do cliente.
**Decisão:** O usuário foi informado do risco em detalhe e decidiu **conscientemente aceitar** por enquanto — ele já tem uma abordagem própria em mente e vai implementar numa sessão futura. Um `spawn_task` (`task_b8b94bec`) foi criado para lembrá-lo ao final da próxima implementação. **Isto NÃO é um esquecimento ou item que passou despercebido** — foi levantado, explicado, e a decisão de adiar foi explícita.
**Alternativas apresentadas (não implementadas ainda):** contador de tentativas por convite (`tentativasConsultaCpf Int @default(0)`) com bloqueio automático do convite após N tentativas erradas de PIN ou M consultas totais.
**Consequências:** Enquanto esta pendência não for resolvida, qualquer pessoa com um link+PIN de convite ativo (vazado, encaminhado por engano, ou obtido por força bruta do PIN) pode gerar custo ilimitado na InfoSimples. Não implementar nenhuma mitigação "criativa" por conta própria em sessões futuras sem antes perguntar ao usuário qual é a abordagem que ele já tinha em mente — ele foi explícito que quer decidir isso.

### 2026-07-06 — CNPJ no convite usa ReceitaFederal existente, não InfoSimples nova
**Contexto:** O usuário pediu inicialmente para usar "a API da InfoSimples" também para CNPJ no wizard de convite. Investigação (Scout) revelou que não existe endpoint de CNPJ via InfoSimples no PainelAlpha — só existe `src/app/api/ReceitaFederal/route.ts` (receitaws.com.br + fallback publica.cnpj.ws), já pública e sem custo por chamada.
**Decisão:** Reaproveitar `ReceitaFederal/route.ts` como está, sem criar uma chamada InfoSimples nova para CNPJ. Confirmado explicitamente com o usuário antes de implementar.
**Alternativas rejeitadas:** Criar novo endpoint InfoSimples para CNPJ (rejeitado pelo usuário — geraria custo adicional por consulta sem necessidade, já que a alternativa gratuita já existe e já retorna os dados completos necessários: razão social, fantasia, endereço, sócios, CNAE, regime tributário).

### 2026-07-06 — Padrão a seguir: nunca aninhar Dialog/modal com hooks dentro de componente com early-return condicional
**Contexto:** Ao implementar o fluxo de mensagem de boas-vindas do convite (`ModalMensagemConvite.tsx`), a primeira versão renderizava esse modal (que usa `Dialog` do Radix, com hooks internos como `useId`) condicionalmente DENTRO do próprio `ModalConvidarParceiro.tsx`, que tem `if (!open) return X`. Isso quebrou em produção-dev com `Rendered more hooks than during the previous render` — o número de hooks/estrutura de árvore mudava entre os dois caminhos de return do mesmo componente.
**Decisão:** Corrigido elevando o estado do modal filho para o componente pai (`ParceirosClient.tsx`): `ModalConvidarParceiro` voltou a ser simples (`if (!open) return null`, sem conhecimento do modal de mensagem) e passou a notificar via callback (`onConviteGerado`). O pai guarda o resultado em estado (`mensagemConvite`) e monta `ModalMensagemConvite` como **irmão independente**, só quando há dados (`{mensagemConvite && <ModalMensagemConvite .../>}`).
**Alternativas rejeitadas:** Manter a renderização condicional dentro do componente com early-return, só ajustando a ordem dos hooks (rejeitado — o problema não é ordem, é a estrutura de árvore divergente entre os dois `return`s; qualquer solução que mantenha dois caminhos de saída com JSX diferente contendo componentes com hooks próprios é frágil).
**Consequências:** **Regra geral para todo o projeto:** ao compor modais (A abre modal B como resultado de uma ação), sempre eleve o estado de B para o ancestral comum mais próximo que não tenha early-return condicional. Nunca monte um Dialog/modal com hooks internos dentro de um componente cujo corpo tem `if (condição) return algo-diferente` antes do fim da função.

### 2026-07-06 — Migration esquecida: coluna `tipo` existia no schema desde 2026-06-18 mas nunca foi aplicada no Turso
**Contexto:** Usuário reportou `The column tipo does not exist in the current database` ao criar template de onboarding. **Decisão:** Aplicada a migration retroativamente via `ALTER TABLE onboarding_template ADD COLUMN tipo TEXT DEFAULT 'USUARIO'` no Turso (Vault aprovado — ADD COLUMN com default, sem risco).
**Alternativas rejeitadas:** Nenhuma — era puramente uma migration esquecida, não uma decisão de design.
**Consequências:** **Isto é a segunda vez nesta sessão que uma "migration fantasma" (existe no schema.prisma, não existe no Turso) causa erro em produção.** Reforça a regra já documentada: sempre que uma coluna nova aparecer no `schema.prisma`, confirmar com `PRAGMA table_info` no Turso real antes de assumir que ela existe — nunca confiar apenas na presença no arquivo de schema.
**Consequências:** A busca de CNPJ no convite não precisa de PIN nem de nenhuma proteção especial contra abuso financeiro — é gratuita. Só a busca de CPF (InfoSimples) tem essa camada de proteção.

### 2026-07-08 — Reescrita completa do módulo de Extratos Bancários: decisão de arquitetura delegada a Bibble
**Contexto:** Usuário pediu reescrita total do módulo (páginas, modais, pipeline OCR, background novo) após meses tentando acertar o sistema. Histórico mostra 3 reversões anteriores no pipeline de extração (Tika+2 agentes → 1 agente → parsers determinísticos por banco REJEITADO → IA por página real do PDF). Perguntado explicitamente se a estratégia OCR deveria mudar de novo e se o schema deveria ser migrado, o usuário respondeu "decida você, quero funcionando" para ambas.

**Consequências:** Esta é a decisão de arquitetura que rege toda a reescrita — qualquer sessão futura mexendo neste módulo deve ler esta entrada antes de propor voltar a parsers regex ou reverter o schema sem motivo novo. ### 2026-07-09 — Migration de Transacao.data executada: dados reais mais irregulares que o previsto, `data` virou nullable
**Contexto:** Ao executar a migration acima, Vault consultou o Turso de produção (autorizado pelo usuário) e descobriu que dos 1015 registros de `Transacao`, só 71,5% (726) tinham `DD/MM/YYYY` completo. 26,8% (272) tinham só `DD/MM` **sem ano**, com `mesReferencia` vazio (sem como inferir o ano com confiança — `createdAt` desses registros é de abril/2026, mas o extrato em si podia ser de qualquer ano anterior). ~1,6% (11) continham texto de "Saldo do dia" confundido com transação pela IA (bug real do pipeline).
**Decisão:** Usuário decidiu explicitamente: (1) os 272 registros sem ano + 1 vazio viram `data = NULL` com o texto original preservado em `dataOriginalTexto` (não inventar ano); (2) os 11 registros de saldo malformado foram excluídos (não são transações reais). Schema final: `data DateTime?` (nullable, não `DateTime` obrigatório como o plano original assumia) + `dataOriginalTexto String?`. Migration executada com sucesso: 731 convertidas (726 DD/MM/YYYY + 5 "DD MES YYYY"), 273 preservadas só como texto, 11 excluídas, 1004 registros finais (1015 - 11). Backup completo (JSON + SQL de restauração) salvo antes de qualquer escrita.
**Alternativas rejeitadas:** Assumir ano corrente para os 272 registros sem ano (rejeitado pelo usuário — introduziria erro sistemático, já que `createdAt` prova que não são todos do ano corrente); manter tudo como estava até investigação manual (rejeitado — travaria a reescrita inteira por uma minoria de registros).
**Consequências:** Qualquer código (actions, componentes) que use `Transacao.data` DEVE tratar `null` como caso válido e comum (27% dos dados legados) — nunca assumir presença. Novas transações salvas a partir de agora (via `SalvarTransacoesLote` reescrita) tentam parsear a data recebida do frontend; se não parsear, também caem em `dataOriginalTexto` com `data = null` — o mesmo padrão de resiliência se aplica prospectivamente, não só aos dados legados.
**Adicionado em:** 2026-07-09.

### 2026-07-09 — Alpha Presentation Studio: arquitetura de dados do slide + reuso de libs já instaladas
**Contexto:** Início do módulo novo "Alpha Presentation Studio" (editor de apresentações HTML interativas, escopo completo pedido pelo usuário — dashboard, editor visual, biblioteca de componentes, animações, 3D, IA generativa, export/publicação, colaboração). Scout mapeou o terreno e levantou 3 decisões de arquitetura antes de liberar o schema para Vault.
**Decisão:** (1) Conteúdo de cada slide (textos, imagens, posições, animações) é armazenado como `Slide.dadosJson Json` — um blob por slide, não uma tabela relacional `ComponenteSlide`. Bate com o padrão já usado no projeto (`dadosBrutos Json` em `ConsultaPreAnalise`, `socios Json?` em `ContratoComercial`) e evita N queries de escrita por autosave num banco SQLite/Turso via rede. (2) Biblioteca de componentes usa **Recharts** para gráficos (não Chart.js) — já é dependência usada em CRM/Metas. (3) Editor usa **@dnd-kit** para drag-and-drop no canvas (não React DnD) — já instalado e usado no projeto.
**Alternativas rejeitadas:** Tabela `ComponenteSlide` relacional (rejeitada — overhead de escrita alto para editor com autosave frequente, sem ganho real já que nunca houve requisito de query relacional dentro do conteúdo do slide); Chart.js e React DnD como pedido literal do prompt original (rejeitados — introduziriam 2ª biblioteca fazendo o mesmo papel de uma já instalada e adotada em outros módulos, duplicação que Lens sempre marca).

Dado o tamanho do escopo total (aprovado pelo usuário como "tudo, completo, sem deixar nada para trás"), a construção será fatiada em ondas sequenciais (schema+registry+dashboard → editor+canvas+básicos → temas+animações → 3D → IA → export/publicação/colaboração), cada onda passando pelo pipeline serial completo — isto não reduz o escopo, apenas ordena a entrega.

### 2026-07-09 — Alpha Presentation Studio Onda 2 (Editor): seleção aninhada e regra do último slide
**Contexto:** Scout mapeou o blueprint do Editor e levantou 2 decisões de produto antes de Echo/Nova implementarem: como funciona a seleção de um componente filho dentro de um Card/Grid (containers aninhados), e se uma apresentação pode ficar com zero slides.
**Decisão:** (1) Clique simples seleciona diretamente o componente filho dentro de um Card/Grid (não o container pai primeiro) — comportamento tipo Figma/Framer, não tipo PowerPoint. Clicar numa área vazia do Card (sem filho embaixo do cursor) seleciona o Card. (2) Apresentação SEMPRE tem no mínimo 1 slide — a ação de excluir o último slide restante é bloqueada (desabilitada/com aviso), nunca permite chegar a zero slides.
**Alternativas rejeitadas:** Seleção por duplo-clique para "entrar" no container (mais passos, rejeitada por adicionar fricção sem necessidade clara neste estágio); permitir zero slides com estado vazio no Editor (rejeitada — mais complexidade de UI para um estado que não agrega valor ao usuário).
**Consequências:** `ComponenteNoCanvas.tsx` precisa detectar clique no filho mais profundo sob o cursor, não just no container mais externo (hit-testing por z-index/profundidade). `ExcluirSlide` (Server Action) deve checar `count(slides) > 1` antes de deletar e retornar erro claro se for o último; a UI (`SidebarSlides.tsx`) deve desabilitar visualmente a ação quando só resta 1 slide.

**⚠️ PENDÊNCIA DE SEGURANÇA REGISTRADA (Anubis, 2026-07-09, Onda 2):** o campo `url` do componente `imagem` (`slide-componentes.ts`) é texto livre controlado pelo usuário via painel de propriedades, hoje só usado client-side (`<img src=...>`, sem risco de XSS — browsers modernos não executam `javascript:` em `src` de imagem). **Quando a Onda 6 (Export Engine) processar essa `url` no SERVIDOR** (ex: baixar a imagem para embutir no HTML exportado, gerar thumbnail), validar o esquema da URL (permitir só `http`/`https`) e considerar allowlist de domínios ou proxy — sem essa validação, um usuário poderia usar a `url` para forçar o servidor a fazer requisições a endereços internos da rede (SSRF).
